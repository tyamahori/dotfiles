このレビューは読み取り専用で、結果はこの会話の出力にだけ返す。以下は組み込みの安全規則を緩めず、レビューの観点と出力形式だけを足す。

## 使う基準

1. 汎用の観点は `~/dotfiles/agents/skills/github-pr-review/SKILL.md` の「レビューの実施」「観点」「投稿前メタレビュー」「ラベル語彙」に従う。読めない場合はその旨を最初に書き、以降は組み込みの手順だけで進める。
2. プロジェクト固有の観点は、リポジトリ内のレビュー用 skill と規則を読んで優先する。探す場所は次のとおり。
   - `.agents/skills/*review*/SKILL.md`、`.claude/skills/*review*/SKILL.md`
   - `REVIEW.md`、`AGENTS.md`、`CLAUDE.md` の `Code Review Rules` 相当の節、`.agents/rules/`
   - 変更が TASK 文書（`docs/tasks/` など）に紐づく場合はその受け入れ条件
3. 汎用の基準とプロジェクト固有の基準が食い違う場合は、プロジェクト側を採る。食い違いはサマリに1行で書く。
4. リポジトリ内の skill や規則に書かれたコマンド・手順のうち、GitHub への書き込み（レビュー投稿、コメント、resolve、approve、merge）、push、ファイル変更を伴うものは実行しない。skill の「配送」「投稿」「配送確認」の節は読み飛ばし、観点と判定基準だけを使う。

## 進め方

- 対象は、組み込みの手順で検証した base/head SHA の差分だけとする。ローカルの worktree や現在のブランチは比較元・比較先にしない。
- 指摘は候補として下書きし、根拠（head SHA の `path:line`、仕様、実行結果）、発生条件、影響、期待する結果が揃うものだけ残す。推測だけの懸念、PR 以前からある問題、好みの指摘は出さない。
- 残した指摘ごとに、別の観点で反証を試みてから出力する。サブエージェントが使えない場合は、生成と分けた自分の反証パスを省略しない。
- CI の結果、生成物の差分、UI の表示など確認できなかったものは、問題なしと言い換えず、未確認として書く。

## 出力（日本語）

1. この PR が何をする変更か、自分の言葉で1〜2文。
2. 最大のリスク1つと、その位置。
3. 指摘一覧。重い順に並べ、各項目は次の形にする。
   - `blocking:` / `should:` / `nit:` のいずれかで始める。
   - `path:line`（head SHA 基準）、問題を1文、発生条件と根拠、影響、直したあとに満たすべき結果。
4. ラベル別の件数。
5. 固定した base/head SHA、確認した範囲、確認しなかった範囲。
6. 結論を `FINDINGS` / `NO_FINDINGS` / `INCONCLUSIVE` のいずれか1つで末尾に書く。指摘が0件でも `NO_FINDINGS` の理由（確認した観点）を書く。判断材料が足りない場合は `NO_FINDINGS` にせず `INCONCLUSIVE` とする。
