## 4. lint で機械的に検出する

```
uv run scripts/lint.py --json <file>
```

禁止語・翻訳調・「〜ではなく」の多用・文の長さの単調さ・体言止めがまったくないこと・語彙の使い回し・英語の構文の直訳などを検出する。文書のジャンルが分かっているなら `--genre essay|tech|business` を付けると、そのジャンルに合わせた閾値になり、誤検出が減る。

lint の指摘は疑いであって、全部直せという指示ではない。各指摘の説明に、何を疑っているかと直し方が書いてある。文脈に照らして、直すか残すかを決める。迷ったら、その一文を声に出して読み、人が話すときの言い回しに近いかで決める。

指摘ごとに、直したか、残したならその理由を一言で記録しながら進める。理由は「固有名詞の一部」「文脈上必要」「技術用語」「ジャンル上自然」などでよい。理由のない「残す」は、判断していないのと同じなので避ける。体言止めがないという指摘は参考情報で、これに合わせて体言止めを足さない(原則8)。記録は応答の中に書けば足りる。ファイルにする場合は §7 に従う。

```
- [直した] translationese「〜という点で」: 「〜では」に言い換えた
- [残す/固有名詞] forbidden_phrase「多角的」: 製品名「多角的レビュー機能」の一部
```

`uv` が使えない環境(Claude.ai など)では、`references/manual-checklist.md` の手順で同じ観点を目で確かめる。

`scripts/semantic.py` は、隣り合う文の意味の似かたから話題の平板さを測る実験的な検出器で、任意で使う。初回に約1GBのモデルをダウンロードするので、フルモードで環境が許すときだけ `uv run scripts/semantic.py --json <file>` を実行し、指摘は lint と同じように扱う。

## 5. 構造と読みやすさを点検する

lint が見るのは文の表面だけである。箇条書きの多い議事録やスライドでは、lint はほとんど何も検出しないので、構成は別に点検する。

### 構造の点検

見出しと各段落の先頭文だけを順に読み、次を確かめる。`uv run scripts/outline.py <file>` で、見出し・各段落の先頭文・箇条書きを行番号つきで抜き出せる。

1. 見出しと先頭文だけで論旨が追えるか
2. 各見出しが結論を言っているか
3. 同じ型(定義文の型、節の組み立て、書き出しの文型)が続いていないか
4. 節ごとに濃淡があるか
5. 読み手が知りたい結論を、後半まで待たせていないか。事実の説明とは別に、「思い込み→異変→種明かし→回収」のような筋書きを追わせていないか。経緯そのものが証拠になる障害調査や、発見の過程を書くエッセイでは、時系列を残してよい
6. 結びが次にすべきことにつながっているか(新しく書くレポートの場合。直す場合は、元の文書に書かれているときだけ見る)

文書タイプが決まっていれば、doctypes のファイルにある必須要素と、AI がやりがちな失敗も照らし合わせる。

### 読みやすさの点検

`uv run scripts/lint.py --reading-load <file>` で、読みにくそうな箇所(長すぎる文、文に埋もれた列挙、続きすぎる漢字、二重否定、「の」の連続、「〜することができる」)を指し示せる。これは AI らしさの検出とは別の検査で、自然度のスコアにも `--baseline` の比較にも入らない。指し示された文は、読み手の手間を増やしているなら直す(§3)。

次の順に確かめる。1〜8は、前のものほど読み手にかかる負担が大きい。9は文書全体を見ないと分からないものなので、§5 の構造の点検と合わせて見る。

1. 否定と条件の入れ子。二重否定や、入れ子になった条件を素直な形にする。直したら、真偽と条件の対応が元の文と同じかを必ず確かめる。「設定が無効でない限り」と「設定が有効なら」は、未設定のときの扱いが違う。書き手が意図して断定を避けている箇所は、意味を変えずに直せないなら触らない
2. 係り受けの距離。一文に主張が二つ以上あれば分ける。主語と述語が離れてねじれていないか、長い修飾語が先に来ているかを見る。読点は、文の構造の切れ目に打つ。「〜が、〜が、」と続く文は分ける。「これ」「それ」が何を指すか、直前の文から一つに決まるかを見る
3. 語の重さ。漢字が7字以上続くと語の切れ目が見えにくくなるので、ひらがなを交えて開く。「の」が3つ以上続く箇所や、「〜の実現」「〜への寄与」のように動作を名詞にした箇所は、誰が何をするかが見えにくいので、動詞に戻す。受け身が続いて動作主が見えなければ、動作主を出す。ただし、出すのは元の文書に動作主が書かれているときだけで、推測で補わない(§3)。読み手によって意味の取り方が変わるカタカナ語は、和語や漢語に言い換える
4. 冗長な言い回し。「〜することができる」は「〜できる」に、「〜という形になる」は「〜になる」にする。情報を増やさずに字数だけを増やしている言い回しなので、削るだけで、足さない
5. 段落。改行のない長い塊はどこで区切って読めばよいか分からず、一文ごとの細切れはつながっている論理を切ってしまうので、どちらも避ける
6. 文に埋もれた列挙。同格の項目が3つ以上あり、一文が長くなっているときだけ、箇条書きに開く。各項目を「太字: 説明」の形にすると、それ自体が AI の書いた文書の典型的な見た目になるので避ける
7. 段落をまたぐ繰り返し。同じことを言い換えて繰り返している段落は、情報が増えない部分だけを削る(§3)
8. 表記ゆれ。同じものは同じ表記にする。`uv run scripts/terms.py <file>` で、専門用語の初出の位置と説明の有無を一覧にできる
9. 構成と読み手の知識。結論が最後まで出ない構成と、説明のないまま使われる専門用語を直す

短くすること自体は目的にしない。まず、必要な事実が残っているか、主語と述語・修飾語と被修飾語が対応しているかを確かめる。その二つが同じくらいの候補どうしでだけ、短いほうを選ぶ。文を分けたり列挙を開いたりして字数が増えるのは、正しい結果である。

## 6. 収束と仕上げ

直した箇所を反映したら lint をもう一度実行する。直前の `--json` 出力を `--baseline` に渡すと、指摘が resolved・new・persisting に分かれるので、new と persisting だけを見ればよい。すべての指摘が「直した」か「残す(理由)」に分かれ、直したことで新しい指摘が出ていなければ、収束とする。回数は決めず、この状態になったら終える。

同じ指摘が2回続けて再発するなら、言い換えを重ねても収束しない。文や段落の組み立てごと書き直すか、理由をつけて残す。

収束したら、仕上げに、直した文書を元の文書と並べ、元にない事実・数値・評価・方針が入っていないかを確かめる(冒頭の規則)。新しく書いた文書なら、素材にない事実が入っていないかを確かめる。新しく書いた文書でも、書いたモデル自身が自然だと感じる言い回しで中身をぼかしやすい(「三つの論点が浮かび上がる」のように、名詞を主語にして中身を言わない書き方など)。§3「読み手が何のことか取れない言い回しは、ふだんの言葉に戻す」の見つけ方で、段落ごとに確かめて直す。

### 読み手の分野の言葉と照らし合わせる

読み手の分野の呼び名から外れた言葉(公開エンドポイントを「入口」、リクエストを「要求」、「失効が効く」「夜間の処理が拾う」)は、書いたモデルが読み返しても気づけない。書いた意図を知っているので、その意図で読めてしまうからだ。指摘されれば直せるので、気づく段階を機械に任せる。書き直すたびに新しく入り込むので、組み直したあとも毎回行う。

1. `uv run scripts/calques.py <file>` で、人や物の動きを機械の処理に当てた動詞(拾う・引く・通る・効く・響く・足す)と、仕組みを場所にたとえた名詞(入口・受け口・口・〜先)の候補を並べる。見出し・表・図の文字も対象にする。判断はしないので、誤検出も出る
2. 挙がった語ごとに、次の2つで決める。この語は、読み手が自分で書くときに使う呼び名か(違うなら、読み手の分野の呼び名に直す)。この動詞だけで、何がどうなるかが分かるか(分からないなら、起きることを書く。「失効が効く」は「次のリクエストから通らなくなる」)。説明として正確に通じる言い方(「トークンを発行するエンドポイント」)は残す

### 元の文書にない事実を洗い出す

既存の文書を直したときは、次のコマンドで、直した文書にだけある数値・固有名詞・英字の語を一覧にできる。元の文書が別のファイルとして残っていれば、それと比べる。git で管理しているファイルを直接書き換えたなら、`--git` を付けると直前のコミットの内容と比べられる。どちらでもなく、git で管理していないファイルを直接書き換えるときだけ、直す前に元の文書を作業用のディレクトリへ写しておく(§7)。

```
uv run scripts/newfacts.py <元の文書> <直した文書>
uv run scripts/newfacts.py --git <直した文書>
```

一覧に出た語が元にない事実なら、削るか元の内容に戻す。略語の正式名称のように、元の文書から直接言える補足なら残してよい。このスクリプトが検出できるのは新しく出てきた数値・固有名詞・英字の語だけで、普通の名詞で足した細部、確信の度合いの変化、発言者の入れ替えは検出できない。何も出なくても、自分の目での確認は省かない。

## 7. 後片付け

作業中に作った中間ファイル(lint の JSON、対応の記録、元の文書の写し、下書きの控えなど)は、対象の文書と同じディレクトリに置かない。環境のスクラッチパッドがあればそこに、なければ `mktemp -d` で作った一時ディレクトリに置く。完了したら一時ディレクトリごと削除する。作業用のファイルがユーザーのプロジェクトに混ざらないようにするためである。ユーザーのプロジェクトに残すのは、完成した文書と、ユーザーが明示的に望んだ場合の `style-profile.md` だけである。
