# github-pr-review

チャットの中にしか存在しないレビューは作者に届かない。PR に投稿して初めて完了。

## 守備範囲

GitHub の PR に対するレビューの実施と配送は、このスキルが正本。近縁の仕組みとの
役割分担:

自分の PR に届いた指摘への対応は `github-pr-respond` を使う。
CI 失敗の調査や通常コメントの投稿だけでは、このレビュー手順を起動しない。
投稿にはユーザーの承認範囲を確認し、このスキルの読込だけを投稿の許可と扱わない。

- 作業中 diff・コミット・ブランチのレビュー → evidence-code-review（`MUST(Functionality):` 等の
  ラベルで返す。PR に配送するときは MUST→`blocking:`、SHOULD→`should:`、NITS→`nit:` に
  読み替え、任意改善の BETTER はインラインにせずサマリへ回す）
- 成果物の深掘り・反証 → adversarial-verification（コードは反例・エッジケース観点）
- 別モデルの目が欲しい → omp-herdr-collab のクロスレビュー（omp から実行）

これらで得た指摘も、対象が PR なら最終的に本スキルの形式で PR 上に配送する。

## レビューの実施

1. **PR の現状と対象コミットを固定する。** merged / closed になっていないか、対象
   スレッドが解決済みでないかを確認する。GitHub API が返す `base.sha` と `head.sha` を
   記録し、この2つの SHA 間の差分をレビュー対象として固定する。ローカルの未コミット
   変更はレビュー対象に含めない。
2. **初回のdiffは固定したPRのbaseコミット基準で読む。** base は main とは限らない
   （develop 宛ての PR もある）。`git diff <base.sha> <head.sha>` のように両方を
   固定 SHA で指定し、必要なら `head.sha` を指すクリーンな worktree または
   `git show <head.sha>:<path>` で内容を読む。ローカルの base や head のブランチ先端、
   現在の作業ツリーを比較元・比較先にしてはならない。
3. **既存の議論と作者の説明を全件確認する。** PR 本文と、各コミットの件名だけでなく
   本文も読む。`--paginate` を付けてレビュー、レビュー本文に紐づくインラインコメント、
   通常の PR コメントをすべて取得する。再レビューでは、以前の指摘ごとに固定した
   `head.sha` で解消・未解消・再発を確認し、解消済みの指摘を重複して投稿しない。
4. **今回の対象diffを読み切るまで探索を始めない。** 再レビューの対象は次節で定める。
   対象diff全体を読み終えて残った疑問は、範囲を絞って確認する。指摘は確認できた
   順に severity 付きで手元の下書きへ逐次記録し、途中で中断されても部分成果が残る
   ようにする（投稿は従来どおり最後に1つのレビュー）。
5. **先に ponytail-review レンズで 1 パス**: 過剰実装（削除・stdlib 置換・
   yagni）だけを拾い、設計指摘として次の観点に合流させる（`nit:` は付けない）。
6. **観点は「観点」節の対応表で問う。** ハンクだけでなく、囲む関数全体を `head.sha` で
   読んでから答える。
7. **コードは変更しない。** レビューのみが既定。修正まで行うのは明示的に
   頼まれたときだけ。

### 同じPRの再レビュー

前回の固定base/head SHA、確認範囲、指摘と検証結果がそろっている場合は、
前回headから今回headまでの全差分、以前の全指摘、変更した契約の影響範囲を
起点にする。変更のないファイルを一律に読み直す必要はない。

囲む関数、呼び出し元、データの受け渡し、関連テスト・文書は、影響を判断できる
範囲まで読む。レビュアー自身が今回の固定SHAのコードと必要な検証で確認し、
実装者の説明や前回の結論だけで解消と判断しない。前回の指摘以外の回帰も確認する。

再レビューで新しく出す指摘は、前回の指摘の未解消・再発、回帰、前回から変わった行の
問題に絞る。前回から変わっていない行には、`blocking:` に当たるもの以外を新しく
出さない。同じ種類の指摘が3回目のレビューでも残るなら、個別の修正を重ねるより
方針を見直すようサマリで提案する。

前回の証拠が欠ける、baseや受入条件が変わる、履歴の書換えで比較が不確か、
影響が想定範囲を超える場合は、今回のbase/head間の全体確認に戻す。
ただし rebase だけの書換えなら、前回と今回の各 commit の `git patch-id --stable`
を比べ、一致した commit はその差分の確認を引き継いでよい。新しい base で変わった
契約や受入条件との突き合わせは引き継がず、一致しない commit と合わせて読み直す。
独立性と投稿前メタレビューは維持する。投稿本文には前回・今回のSHAと、
今回確認した範囲、再利用した証拠、未確認範囲を明記する。

### 観点

全 PR に共通の質問と、変更種別ごとに必ず問う質問の2段。PR に含まれる変更種別を
すべて拾い、該当行の質問に答えられるまで読む。答えが「分からない」なら、その旨を
INCONCLUSIVE の材料として残す。

共通:

- 正しさ: 境界値・空・重複で壊れないか。リトライ、少なくとも1回届く配送、途中失敗後の
  再実行がありうる経路では、2回目の実行で期待どおりの結果（重複の拒否か許容か）に
  なるか。追記・採番・課金・通知のように意図して冪等でない処理は、その期待を確かめる。
  状態・時刻・依存先の失敗・並行実行は test-design スキルの観点表の行を、コード上の
  経路で答える。並行実行の指摘には、実際に同時に走る2つの経路を示す
- 設計: 変更の形が課題に合っているか。PR 説明の主張（「挙動変更なし」「テスト済み」）と
  diff が一致しているか。課題に無関係な変更が混ざっていないか
- 再利用と一貫性: 新しく書いた処理・型・定数と同じ責務の既存 helper や、隣接
  ファイルで確立した書き方がリポジトリ内にあるか。指摘するときは既存側を
  `path:line` で示す
- 型と不変条件: 新しい型や設定の形で、この diff の呼び出し元が矛盾した状態を作れるか。
  作れるなら構築時か型で防いでいるか。作れる呼び出し元を示せなければ指摘しない
- 複雑さ: 次に読む人がすぐ理解できるか、呼び出し・変更するときに壊しやすくないか。
  いま必要のない汎用化は `should:` で指摘する
- 大きさ: 1つのコミットにリファクタと挙動変更が混ざっている、または手書きの差分が
  目安400行を超えるなら、深く読めなかった範囲をサマリに書き、分割を提案する
- テスト: 変更後の挙動が仕様として固定されているか。コードが壊れれば落ち、無関係な
  変更では落ちないか。assert が境界そのものを見ているか（mock の呼び出しをなぞる
  だけになっていないか）
- 知識の置き場所: コミットログは Why、コードコメントは Why-not、テスト名は挙動の
  What。次行の動作をなぞるだけのコメントや呼び出すメソッド名をなぞっただけの
  テスト名は `nit:` で指摘し、Why のないコミットメッセージは行アンカーできないので
  サマリで扱う。読んで理解できなかったコードは、PR 上の説明で済ませず、書き直すか
  コードに Why コメントを残すよう求める
- コメントと docs の正確さ: 変更したコメント・名前・TODO・docs が書く事実（「同じ」
  「〜だけ」「〜を呼ぶ」）を、参照先のコードで確かめる。変更後の挙動と食い違うなら、
  読み手を誤らせるので `should:` にする。この変更で事実と合わなくなった差分外の
  既存コメント・docs は、ラベルを付けずにサマリで指摘する

変更種別ごと:

| 変更種別 | 必ず問う質問 |
|---|---|
| バグ修正 | 修正を戻すとそのテストは落ちるか。同じ原因を持つ兄弟経路（同じ関数の他の呼び出し元、同じパターンの隣接コード）も直っているか |
| 挙動を変えないはずの変更（リファクタ・整理） | 挙動不変の根拠は何か（既存テスト、出力比較）。挙動変更が混ざっていないか |
| 公開シンボル・API の変更 | 参照元を全件列挙して未更新の呼び出し元がないか。新しい API に同じ PR 内の利用箇所があるか。削除したコードの docs も消えているか。互換性を壊すなら利用者向けの告知・docs が同じ変更に入っているか |
| 新しい入口（endpoint・コマンド・ハンドラ・イベント購読） | 認証・認可はあるか。入力検証は境界にあるか。失敗時の応答を呼び出し側が扱えるか |
| データアクセス（クエリ・ファイル I/O・外部呼び出し） | データ量に比例して壊れないか（ループ内 I/O、N+1、無制限取得、新クエリのインデックス）。インジェクション・パス走査。タイムアウトと失敗時の扱い |
| スキーマ・migration | 旧コードと同時稼働する瞬間に壊れないか。ロールバックできるか。大きいテーブルでロックを取らないか |
| 設定・環境変数・CLI 引数・運用手順 | docs・デプロイ手順・デフォルト値が同じ変更に入っているか。未設定時の挙動は定義されているか |
| 依存更新 | changelog の破壊的変更、ライセンス、lockfile 差分が意図した範囲か |
| ログ・エラー処理 | 障害時に原因へたどり着ける情報か。PII・秘密情報を出していないか。失敗を握りつぶす・別の値に置き換える経路（空の catch、広すぎる catch、ログだけで継続、null・空・既定値の返却、フォールバック）で、呼び出し側が成功と失敗を区別でき、原因が残るか。開いたファイル・プロセス・ロック・一時ファイルは、例外や早期 return の経路でも解放されるか |
| CI・ビルド・スクリプト | 失敗が失敗として伝播するか（終了コード、`pipefail` 下のパイプ）。ローカルと CI で同じ結果になるか |
| UI・利用者に見える出力（画面・CLI の出力・メッセージ） | 実際の表示をスクリーンショットや実行結果で確かめられるか。確かめられないなら未確認の範囲としてサマリに書く |

表にない種別に当たったら、その変更が壊すものを1つ想定し、同じ形の質問を作って答える。

`JEV_API_KEY` がある環境では、確定した変更種別の行を `docs/jev.md` の「Jev PR-review
lens shadow」の手順で任意にログできる。レビューの判断と完了条件には影響しない。

## 投稿前メタレビュー

根拠や対応価値の薄い指摘を除き、レビューの信号対雑音比を上げる。指摘数の最小化は
狙わない。出典を示せるリポジトリ規約に基づき、作者が具体的に対応できる `nit:` は
1レビュー5件まで残す。超える分は効果の大きい順に選び、残りは件数だけサマリに書く。

GitHub へ送る前に、各指摘を次の項目を持つ候補として内部下書きへ記録する。

- `severity`: 配送の形で定義するラベル語彙（`blocking` / `should` / `nit`）
- `path`、`line`、必要なら `start_line` と `side`
- `claim`: 問題だと判断した内容
- `evidence`: 固定した `head.sha` で読んだ `path:line`、仕様、実行結果のいずれか。
  名前・コメント・PR 説明からの推測だけでは根拠にしない。リポジトリ規約が根拠なら、
  規約ファイルと最小の行範囲を示し、その規約が対象ファイルに適用されることを確かめる
- `trigger`: 問題が起きる入力・状態・環境。`blocking` と `should` では必須で、
  ラベルの重さはこの条件の起きやすさに合わせる
- `impact`: 放置した場合に起きること。他のコードへの影響を主張するなら、実際に読んで
  確かめた影響先のファイルやシンボルを挙げる
- `expected_action`: 解消後に満たすべき結果。実装方法の指定は必須ではない

候補を生成した文脈から切り離した fresh context の reviewer に、固定した
base/head SHA、候補が参照する diff ハンク、関連する既存スレッド、候補の下書きだけを
渡して反証させる。PR 全体を最初から再レビューさせてはならない。候補の確認中に新しい
重大な問題を見つけた場合だけ、根拠付きの新規候補として返させる。fresh reviewer を
利用できない場合も、候補生成とは分けた明示的な反証パスを省略しない。

候補が0件の場合は、今回の対象diff全体、既存スレッド、確認した観点、NO_FINDINGSの
結論を渡し、見落としと証拠不足を反証させる。再レビューでは前回の固定SHA・確認範囲・
検証証拠も渡す。新しいstyle指摘を増やすことを目的にせず、NO_FINDINGSと判断できない
なら不足情報を示してINCONCLUSIVEとする。

各候補を次のいずれかに分類し、理由を内部下書きへ残す。

- **KEEP**: PR 起因で、根拠、発生条件、影響、期待する結果が明確。既存議論や
  他候補とも重複せず、作者が対応する価値がある
- **REWRITE**: 問題は有効だが、断定が根拠より強い、深刻さが発生条件に見合わない、
  影響が不明、修正方法を不必要に限定している、長すぎる、またはアンカー範囲が
  不適切。書き直した後に同じ基準を再確認し、解消できなければ DROP
- **DROP**: 既存議論との重複、PR 以前からある問題（PR が足した・変えたコードの経路で
  初めて起きるものは除く）、差分外の要求、根拠のない懸念、影響先を示せない「影響する
  かもしれない」、作者の意図を推測しないと成り立たない指摘、明らかに意図された変更や
  コミット本文・PR 本文で作者が受け入れを明示した制約への異論、周囲のコードにない
  厳密さの要求、lint 抑止コメントなどで意図的に黙らせた箇所、対応内容が分からない
  感想、自動化だけで完結する指摘、個人的な好み、または対応コストに対して効果が
  極端に小さいもの

同じ原因の問題が複数箇所にあるときは、代表の1箇所に1件だけ置き、本文で全箇所を
挙げて、すべて直すことを expected_action にする。

セキュリティの指摘は、信頼できない入力から危険な処理までの経路をコードで示せるものに
限る。堅牢化の提案だけのもの、DoS・レート制限、理論上の競合状態、環境変数や CLI
引数を信頼できない入力とみなすものは、脆弱性として出さない。

DROP した主張の詳細は GitHub に書かない。最終的な指摘が0件になった理由を説明できる
よう、DROP の理由ごとの件数だけを保持する。

メタレビュー後の状態を次の3つに決める。

- **FINDINGS**: KEEP または書き直し済みの REWRITE が1件以上ある
- **NO_FINDINGS**: 必要な情報を確認でき、投稿に値する指摘が0件
- **INCONCLUSIVE**: CI、仕様、generated diff など判断に必要な情報が不足し、
  問題なしとは判断できない

投稿直前に `head.sha` を再取得する。固定した SHA から変わっていた場合は、影響する
候補、結論、行アンカーを新しい SHA で再検証するまで投稿しない。

## 配送の形

単発コメントの連投ではなく、**1つのレビュー**として投稿する。本文は必須で、
FINDINGS の場合だけ日本語の行アンカー付きインラインコメントを含める。

event は全状態で **COMMENT 固定**。APPROVE / REQUEST_CHANGES はマージ可否の判断であり、
エージェントではなく人間が行う。

### ラベル語彙

インラインコメントは先頭に severity ラベルを固定で置く。語彙は3つだけ:

- `blocking:` マージ前に直さないと壊れる、データを失う、またはセキュリティ境界を破る。
  根拠は実行結果かコード上の具体的な経路に限る
- `should:` 直すべきだが今回のマージを止めるほどではない（変更した挙動を固定する
  テストの欠落、設計のズレ、性能・運用の懸念）
- `nit:` スタイル・命名・テスト名・動作をなぞるだけのコメント。文書化されたリポジトリ
  規約に基づき、作者が具体的に対応できるものだけ

ラベルは優先度の伝達であってマージ可否ではない。`blocking:` があっても event は
COMMENT のまま。

### インライン本文の型

下書きの項目をそのまま並べる。1文目で何が問題かが分かり、続きで根拠と対応後の
状態が分かる形:

```text
<label>: <claim を1文で>

<trigger: 問題が起きる入力・状態>のとき、<evidence: 該当する経路・仕様・実行結果>。
<impact: 放置すると起きること>。<expected_action: 解消後に満たすべき結果>
```

claim の後の本文は1段落に収め、引用するコードは3行までにする。アンカー範囲は問題の
行に絞り、10行を超えない。場所の言い直しや賛辞は書かず、深刻さを発生条件以上に
書かない。作者が読み返さずに要点をつかめる長さを目安にする。

差し替えだけで問題が解消し、数行で済むなら ` ```suggestion ` ブロックを付ける。
作者がワンクリックで適用でき、意図の誤読も防げる。suggestion はアンカー範囲
（`start_line`〜`line`）の行をそのまま置き換えるので、範囲と提案の行数を一致させ、
インデントも元の行に合わせる。設計判断を含む修正や部分的にしか直らない修正には
使わず、expected_action に留める。

### サマリ本文の型（FINDINGS）

次の順で書く。1 は理解のズレを作者に見せるためのもので、省略しない:

1. この PR が何をする変更か、自分の言葉で1〜2文
2. 最大のリスク1つと、対応するインラインの位置
3. ラベル別の件数
4. 確認した範囲と確認しなかった範囲（CI 未確認、generated diff を読んでいない等）

### 投稿

日本語本文は引用符・バッククォート・改行でシェル引用が壊れるので、`-f` / `-F` を
並べる形は使わず、JSON を組んで `--input -` で渡す:

```sh
gh api repos/<owner>/<repo>/pulls/<N>/reviews --input - <<'JSON'
{
  "event": "COMMENT",
  "body": "<全体サマリ（日本語）>",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "body": "<単一行への指摘>" },
    { "path": "src/foo.ts", "start_line": 10, "line": 14, "body": "<複数行（10〜14行）への指摘>" },
    { "path": "src/bar.ts", "side": "LEFT", "line": 7, "body": "<削除された行への指摘>" }
  ]
}
JSON
```

NO_FINDINGS と INCONCLUSIVE は `comments` を省略した本文だけのレビューとして送る。
指摘0件を配送しない理由にしてはならない。

- **NO_FINDINGS**: 確認した観点と、PR 起因で根拠があり対応を要する指摘がなかった
  ことを書く。候補を DROP した場合は、誤った主張を再掲せず分類と件数を集約する。
  候補自体がなければ、除外理由を作らない
- **INCONCLUSIVE**: 取得できなかった情報と、そのため確認できない判断を書く。
  「問題なし」「指摘なし」と言い換えてはならず、必要なら再レビュー条件を示す

NO_FINDINGS の本文例:

```text
固定した base/head SHA 間の差分について、正しさ、変更目的との整合、テスト、
セキュリティ、既存議論との重複を確認しました。今回の変更に起因し、根拠があり、
作者による対応が必要な指摘はありませんでした。

候補3件は、既存議論との重複2件、PR 以前から存在する事項1件だったため、
インラインコメントにはしていません。
```

候補がなければ第2段落を省く。INCONCLUSIVE の本文では、同じ位置に不足情報と
未確認の範囲を書く。

- `line` は diff 適用後のファイル行。複数行にまたがる指摘は `start_line`（先頭）と
  `line`（末尾）で範囲指定する。
- `side` の既定は RIGHT（追加行・文脈行）。削除された行は RIGHT 側に存在しない
  ので `"side": "LEFT"` を指定する。

投稿の応答からレビュー ID を記録し、配送完了と述べる前に
`repos/<owner>/<repo>/pulls/<N>/reviews/<review-id>` を再取得して event が `COMMENT`
であることを確認する。続けてそのレビューのインラインコメントを `--paginate` で取得し、
投稿した件数と一致することを確認する。NO_FINDINGS と INCONCLUSIVE は0件が正常。
ID が取得できない、event が異なる、または件数が一致しない場合は、配送完了を
主張せず状況を報告する。

## 422 を避ける

インラインコメントが1つでも diff に含まれない行を指すと、GitHub はサマリ込みで
レビュー**全体**を拒否する（422）。投稿前に全 `(path, line)` が次の範囲に入るかを
確かめる。出力は `開始行+行数` で、RIGHT は追加行と文脈行、LEFT は削除行と文脈行:

```sh
gh api repos/<owner>/<repo>/pulls/<N>/files --paginate --jq '.[] | .filename as $f
  | (.patch // "") | scan("@@ -(\\d+)(?:,(\\d+))? \\+(\\d+)(?:,(\\d+))? @@")
  | "\($f) LEFT \(.[0])+\(.[1] // "1") RIGHT \(.[2])+\(.[3] // "1")"'
```

`--paginate` を忘れない。既定では30ファイルで切れるため、大きい PR では検証漏れが
そのまま 422 になる。patch が返らないファイル（バイナリ、巨大な diff）はこの検査では
範囲を出せないので、アンカーするなら `git diff <base.sha> <head.sha> -- <path>` の
ハンク見出しで行を確かめる。diff が触っていない箇所への言及はサマリに書く。
