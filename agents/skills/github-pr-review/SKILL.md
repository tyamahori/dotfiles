# github-pr-review

チャットの中にしか存在しないレビューは作者に届かない。PR に投稿して初めて完了。

## 守備範囲

GitHub の PR に対するレビューの実施と配送は、このスキルが正本。近縁の仕組みとの
役割分担:

- 作業中 diff・ブランチのレビュー → 組み込みの /code-review
- 成果物の深掘り・反証 → adversarial-verification（コードは反例・エッジケース観点）
- 別モデルの目が欲しい → omp-herdr-collab のクロスレビュー（omp から実行）

これらで得た指摘も、対象が PR なら最終的に本スキルの形式で PR 上に配送する。

## レビューの実施

1. **PR の現状と対象コミットを固定する。** merged / closed になっていないか、対象
   スレッドが解決済みでないかを確認する。GitHub API が返す `base.sha` と `head.sha` を
   記録し、この2つの SHA 間の差分をレビュー対象として固定する。ローカルの未コミット
   変更はレビュー対象に含めない。
2. **diff は固定した PR の base コミット基準で読む。** base は main とは限らない
   （develop 宛ての PR もある）。`git diff <base.sha> <head.sha>` のように両方を
   固定 SHA で指定し、必要なら `head.sha` を指すクリーンな worktree または
   `git show <head.sha>:<path>` で内容を読む。ローカルの base や head のブランチ先端、
   現在の作業ツリーを比較元・比較先にしてはならない。
3. **既存の議論を全件確認する。** `--paginate` を付けてレビュー、レビュー本文に
   紐づくインラインコメント、通常の PR コメントをすべて取得する。再レビューでは、
   以前の指摘ごとに固定した `head.sha` で解消・未解消・再発を確認し、解消済みの指摘を
   重複して投稿しない。
4. **diff を読み切るまで探索を始めない。** リポジトリ横断の探索コマンドを重ねるのは、
   diff 全体を読み終えて残った疑問を対象を絞って確認するときだけ。指摘は確認できた
   順に severity 付きで手元の下書きへ逐次記録し、途中で中断されても部分成果が残る
   ようにする（投稿は従来どおり最後に1つのレビュー）。
5. **観点**: 正しさ（バグ・境界・競合）、設計（変更の形が課題に合っているか）、
   テスト（変更後の挙動が仕様として固定されているか）、セキュリティ
   （システム境界での検証）、知識の置き場所（コミットログは Why、コード
   コメントは Why-not、テスト名は挙動の What）。次行の動作をなぞるだけの
   コメントや呼び出すメソッド名をなぞっただけのテスト名は `nit:` で指摘し、
   Why のないコミットメッセージは行アンカーできないのでサマリで扱う。
   スタイルの指摘は `nit:` を付けて区別する。
6. **コードは変更しない。** レビューのみが既定。修正まで行うのは明示的に
   頼まれたときだけ。

## 投稿前メタレビュー

根拠や対応価値の薄い指摘を除き、レビューの信号対雑音比を上げる。指摘数の最小化は
狙わない。リポジトリ規約に基づき、作者が具体的に対応できる `nit:` は残す。

GitHub へ送る前に、各指摘を次の項目を持つ候補として内部下書きへ記録する。

- `severity`
- `path`、`line`、必要なら `start_line` と `side`
- `claim`: 問題だと判断した内容
- `evidence`: コード、仕様、実行結果のいずれかによる根拠
- `impact`: 放置した場合に起きること
- `expected_action`: 解消後に満たすべき結果。実装方法の指定は必須ではない

候補を生成した文脈から切り離した fresh context の reviewer に、固定した
base/head SHA、候補が参照する diff ハンク、関連する既存スレッド、候補の下書きだけを
渡して反証させる。PR 全体を最初から再レビューさせてはならない。候補の確認中に新しい
重大な問題を見つけた場合だけ、根拠付きの新規候補として返させる。fresh reviewer を
利用できない場合も、候補生成とは分けた明示的な反証パスを省略しない。

候補が0件の場合は、固定した diff 全体、既存スレッド、確認した観点、NO_FINDINGS の
結論を渡し、見落としと証拠不足を反証させる。この場合も新しい style 指摘を増やすことを
目的にせず、NO_FINDINGS と判断できないなら不足情報を示して INCONCLUSIVE とする。

各候補を次のいずれかに分類し、理由を内部下書きへ残す。

- **KEEP**: PR 起因で、根拠、影響、期待する結果が明確。既存議論や他候補とも
  重複せず、作者が対応する価値がある
- **REWRITE**: 問題は有効だが、断定が根拠より強い、影響が不明、修正方法を
  不必要に限定している、長すぎる、またはアンカー範囲が不適切。書き直した後に
  同じ基準を再確認し、解消できなければ DROP
- **DROP**: 既存議論との重複、PR 以前からある問題、差分外の要求、根拠のない懸念、
  対応内容が分からない感想、自動化だけで完結する指摘、個人的な好み、同じ原因の
  重複指摘、または対応コストに対して効果が極端に小さいもの

DROP した主張の詳細は GitHub に書かない。最終的な指摘が0件になった理由を説明できる
よう、`duplicate`、`pre-existing`、`out-of-scope`、`unsubstantiated`、
`non-actionable`、`automation-only`、`low-value` の分類と件数だけを保持する。

メタレビュー後の状態を次の3つに決める。

- **FINDINGS**: KEEP または書き直し済みの REWRITE が1件以上ある
- **NO_FINDINGS**: 必要な情報を確認でき、投稿に値する指摘が0件
- **INCONCLUSIVE**: CI、仕様、generated diff など判断に必要な情報が不足し、
  問題なしとは判断できない

投稿直前に `head.sha` を再取得する。固定した SHA から変わっていた場合は、影響する
候補、結論、行アンカーを新しい SHA で再検証するまで投稿しない。

## 配送の形

単発コメントの連投ではなく、**1つのレビュー**として投稿する。本文は必須で、
FINDINGS の場合だけ日本語の行アンカー付きインラインコメントを含める。

event は全状態で **COMMENT 固定**。APPROVE / REQUEST_CHANGES はマージ可否の判断であり、
エージェントではなく人間が行う。

日本語本文は引用符・バッククォート・改行でシェル引用が壊れるので、`-f` / `-F` を
並べる形は使わず、JSON を組んで `--input -` で渡す:

```sh
gh api repos/<owner>/<repo>/pulls/<N>/reviews --input - <<'JSON'
{
  "event": "COMMENT",
  "body": "<全体サマリ（日本語）>",
  "comments": [
    { "path": "src/foo.ts", "line": 42, "body": "<単一行への指摘>" },
    { "path": "src/foo.ts", "start_line": 10, "line": 14, "body": "<複数行（10〜14行）への指摘>" },
    { "path": "src/bar.ts", "side": "LEFT", "line": 7, "body": "<削除された行への指摘>" }
  ]
}
JSON
```

NO_FINDINGS と INCONCLUSIVE は `comments` を省略した本文だけのレビューとして送る。
指摘0件を配送しない理由にしてはならない。

- **NO_FINDINGS**: 確認した観点と、PR 起因で根拠があり対応を要する指摘がなかった
  ことを書く。候補を DROP した場合は、誤った主張を再掲せず分類と件数を集約する。
  候補自体がなければ、除外理由を作らない
- **INCONCLUSIVE**: 取得できなかった情報と、そのため確認できない判断を書く。
  「問題なし」「指摘なし」と言い換えてはならず、必要なら再レビュー条件を示す

NO_FINDINGS の本文例:

```text
固定した base/head SHA 間の差分について、正しさ、変更目的との整合、テスト、
セキュリティ、既存議論との重複を確認しました。今回の変更に起因し、根拠があり、
作者による対応が必要な指摘はありませんでした。

候補3件は、既存議論との重複2件、PR 以前から存在する事項1件だったため、
インラインコメントにはしていません。
```

候補がなければ第2段落を省く。INCONCLUSIVE の本文では、同じ位置に不足情報と
未確認の範囲を書く。

- `line` は diff 適用後のファイル行。複数行にまたがる指摘は `start_line`（先頭）と
  `line`（末尾）で範囲指定する。
- `side` の既定は RIGHT（追加行・文脈行）。削除された行は RIGHT 側に存在しない
  ので `"side": "LEFT"` を指定する。

投稿の応答からレビュー ID を記録し、配送完了と述べる前に
`repos/<owner>/<repo>/pulls/<N>/reviews/<review-id>` を再取得して event が `COMMENT`
であることを確認する。続けてそのレビューのインラインコメントを `--paginate` で取得し、
投稿した件数と一致することを確認する。NO_FINDINGS と INCONCLUSIVE は0件が正常。
ID が取得できない、event が異なる、または件数が一致しない場合は、配送完了を
主張せず状況を報告する。

## 422 を避ける

インラインコメントが1つでも diff に含まれない行を指すと、GitHub はサマリ込みで
レビュー**全体**を拒否する（422）。投稿前に全 `(path, line)` をハンクと突き合わせる:

```sh
gh api repos/<owner>/<repo>/pulls/<N>/files --paginate \
  --jq '.[] | "\(.filename)\n\(.patch)"'
```

`--paginate` を忘れない。既定では30ファイルで切れるため、大きい PR では検証漏れが
そのまま 422 になる。ハンクに現れる行だけがアンカー可能で、diff が触っていない
箇所への言及はサマリに書く。
