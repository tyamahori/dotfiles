# create-verification-skill

対象リポジトリに `verify-<app>` skill を作る。読むのは人ではなく、作業の途中でアプリを初めて見るエージェントである。起動、正常性の確認、操作、証拠の採取、後片付けを、そのリポジトリの実際のコマンドとセレクタで書く。汎用のブラウザ操作手順は `browser-verify` にあり、ここではそれをアプリ固有の手順に落とす。

## 置き場所

対象リポジトリに project-local skill の置き場所の規約があれば、それに従う。なければ正本を `.agents/skills/verify-<app>/` に置き（Codex と OMP が読む）、`.claude/skills/verify-<app>` から相対 symlink を張る（Claude Code が読む）。dotfiles の global skill にはしない。

## 生成

### 1. ユーザーではなくリポジトリに聞く

次をコードベースから答え、観測できないことだけをユーザーに聞く。

- **面**: 利用者が触るもの。Web UI、CLI/TUI、デスクトップアプリ、API、ライブラリ。複数あれば主なものを選び、残りを書き留める。
- **起動**: リポジトリ自身の dev コマンド（package scripts、Makefile、README、compose）。ポート、環境変数、seed データ、認証も。Docker で動くなら `orbstack-dev` を先に読む。
- **操作**: 既存の仕組みを先に探す（Playwright/Cypress の spec、expect スクリプト、curl できるエンドポイント、デバッグポート）。なければ Web は `browser-verify` の経路、CLI/TUI は PTY か tmux、サービスは素の HTTP にする。
- **観測**: 取れる証拠。スクリーンショット、端末の出力、レスポンス本文、ログ、終了コード、DB の状態。
- **分離**: 二つのインスタンスを並べて動かせるか（ポート、データディレクトリ、プロファイル）。動かせないなら、共有インスタンスを二重に操作しないと生成物に書く。

checkout がそのままでは build も起動もできないなら、先に直すか正確に報告する。壊れた土台の上で書いた手順は、間違った手順を教える。

### 2. skill を書く

`SKILL.md` に frontmatter（`name: verify-<app>` と、アプリ名・面・使う場面を書いた `description`）と次の節を置く。どの節も調べた結果で埋め、プレースホルダーを残さない。

- **Launch**: 検証用にアプリを起動する正確なコマンドと、準備完了の判定（ログの一行、プロンプト）。空のデータディレクトリから migration と seed まで済んで使える状態になること。プロセスが応答するだけでは準備完了ではない。終了方法も書く。短命な CLI なら、build を一度だけ行い、操作ごとに分離した PTY を起こす。
- **Doctor**: 読み取り専用で「このインスタンスは操作する価値があるか」を答える一つの確認。プロセス、ビルドの版、自分が起動したポートか、認証の有効性。何かおかしいときは最初にこれを走らせる。
- **Drive**: このリポジトリの実際のセレクタやコマンドで書いた操作手順。座標やタブ順ではなく、ARIA ラベル、data 属性、プロンプト文字列、ルートのような安定した手がかりを使う。
- **Evidence**: 何を採取してどこに置くか（既定は `<git toplevel>/.agent-msgs/screenshots/` などの `.agent-msgs/` 配下）。利用者と同じ経路を通り、内部の setter やテスト専用エンドポイントを使わない。操作と結果の状態の両方を取り、画面に見えるものと並べて副作用（書かれたファイル、挿入された行、送られたメッセージ）も確かめる。dry-run や test mode を安全策にするときは、名前を信じず、実際に何を省いているかをファイル・通信・git ref で観測する。
- **Cleanup**: その実行が起動したものだけを止める。プロセス名で kill しない。後片付けは証拠を消さない。
- **Helpers**: 同梱するスクリプトは実行権限を付け、本文に呼び出し方を書く。

### 3. 機能の地図を作る

`features/README.md` と、利用者から見える機能ごとに一ファイルを作る。最初はルート、コマンド、メニュー、ドキュメントから上位3〜5件でよい。各ファイルの見出しは `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas` の四つにする。`Driving it with <harness>` の操作は、コマンドと、それで観測できる結果の組で書く。結果を確かめられない操作は載せない。保存や書き込みは「保存しました」の表示ではなく、開き直して読み戻した値で確かめる。seed データに前提が欠けていて手順が通らないなら、手順を弱めずに失敗として報告し、理由を `Gotchas` に書く。

### 4. 渡す前に生成した skill を実行する

生成物の手順どおりに一度通す。起動、Doctor、地図にある機能を一つ操作、証拠の採取、後片付け。後片付けの後に、証拠が指定した場所に残っていることを確かめる。失敗したら直し、失敗した回の後にも Cleanup を走らせて、プロセスやポートを残さない。一度も実行していない生成物は下書きであり、成果物ではない。本番と違う代用環境（実 VM の代わりにコンテナなど）で確かめたなら、代用環境だけが行った準備を列挙し、未検証として報告する。

## 保守

アプリが変わると地図は古くなる。「verify skill を直して」と言われたら、既存の `verify-*` skill について次を行う。対象が見つからなければ、保守を始めずに生成へ回る。

1. 地図の索引を直す。README と実際のファイルの抜け、余り、重複、死んだリンク。
2. 機能ファイルごとに読み取り専用の subagent を並列に起こし、その機能がソース上でどう動くかを説明させる。地図とのずれを `file:line` 付きで挙げさせ、ライブ確認の手順を一つ返させる。subagent はアプリを操作せず、ファイルも編集しない。
3. 結果を突き合わせる。最近の変更で増えた利用者向けの面が地図になければ、具体的なソースパスを示せるときだけ「欠落」と呼ぶ。
4. ソースがきれいに見えても、全機能を一度はライブで操作する。最初の操作の前と、操作が失敗するたびに Doctor を走らせる。採取済みの証拠はどの後片付けの後も残す。到達できない機能は、欠けている前提（認証、権限、OS、外部状態）と試した経路を添えて「到達不能」とする。
5. 振り分ける。先に観測側を疑う。古いスクリーンショット、残ったブラウザ状態やキャッシュ、別のインスタンスを見ていないかを確かめ、観測が正しいと分かってから対象の問題として扱う。説明の誤りは地図を直す。動いているのに操作できないものはハーネスを直し、直したらライブで再確認する。アプリ自体が壊れているものは製品の不具合としてユーザーに報告し、地図を書き換えて隠さない。
6. 直すのは skill 自身のディレクトリだけで、製品コードには触れない。結果は「変更なし」「修正あり（一つの変更にまとめる）」「中断（理由つき）」のどれかで報告する。
