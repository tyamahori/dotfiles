# 詳細手順

本文中の `scripts/`、`references/`、`templates/` とコマンドの相対パスは、
このファイルではなく当該 skill のルートを基準にする。

### 実行効率

Bash 比率や tool 呼び出し数の少なさを目標にしない。
同じ成果を得るまでの処理回数、待ち時間、再作業を、品質と合わせて評価する。
タスク全体の成功が取得不能なら、成功条件を確認できる処理単位で比較する。
その結果をタスク全体の効率や成功率へ一般化しない。

調査対象は、専用ツールで代替できる処理、取得後に捨てた大きな出力、拒否や待機からの回復、同じ処理の手書き反復である。
各 host が使えるツールを確認し、正常な CLI 実行、意図した否定系検証、ユーザー要求による反復を無駄と数えない。
呼び出しと結果を ID で対応付け、終了コードだけでなく、その処理の成功条件を満たしたかを確認する。
大きな結果や raw error flag は調査の入口であり、それだけでは失敗や削減可能量を示さない。

改善ごとに journal 内で同じ識別子を使い、対象処理、根拠、基準値、変更内容、品質条件、次回確認日を残す。
基準値には期間の開始・終了とタイムゾーン、host と実行環境、入力規模、対象件数、集計方法を含める。
成功までの呼び出し数、失敗後の再試行数、結果サイズ、観測できる実経過時間を記録し、取得不能は 0 で代用しない。
並列の tool 所要時間の合計や model 応答時間を、処理の実経過時間として扱わない。

次回は同種の処理と品質条件で比較し、継続、撤回提案、判定保留のいずれかを記録する。
環境や入力条件が変わった場合、対象処理が再発していない場合、観測が不足する場合は、効果を断定せず次の確認条件を残す。
撤回も項目別承認を経て行い、安全性や成果の正しさを落として短縮した処理は改善と認めない。
診断自身の再走査や重複調査も対象とし、同じ条件の snapshot を再利用して不足する根拠だけを補う。
