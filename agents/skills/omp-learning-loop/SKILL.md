# omp-learning-loop

OMP の学習候補を「収集 → 裏取り → 仕分け → 項目別承認 → 昇格 → 実動確認」の順で扱う。

## 起動方法

シェルでは対象リポジトリへ移動してから `omp-learning-review` を実行する。
このコマンドがレビュー専用の新しいOMPセッションを起動するため、OMP内では実行しない。

既存のOMPセッションでは `/skill:omp-learning-loop` を実行する。
どちらの入口も起動時の cwd に対応するプロジェクトだけをレビューする。

この skill は学習結果を無条件に正しいものとして扱わない。
Memory は過去セッションから抽出したヒューリスティックであり、現在のリポジトリ、実行結果、ユーザー指示を優先する。

## 対象範囲

1 回のレビューでは、起動時の cwd に対応するプロジェクトだけを扱う。
候補は次の三系統から集める。

- `memory://root/learned.md`：`learn` が明示的に保存したlesson。
- `memory://root/skills/`：local memory の統合処理が生成したplaybook。
- `~/.omp/agent/managed-skills/`：`learn` または `manage_skill` が作成したmanaged skill。

`memory://root/MEMORY.md` と `memory://root/memory_summary.md` は候補の背景確認に使う。
ファイルやディレクトリが存在しない場合は、候補なしとして続行する。

## 収集

最初に候補の一覧と更新内容を読む。
全文を一括で会話へ貼らず、候補ごとに必要な範囲だけ読む。

次に、各候補が参照する現在のコード、設定、テスト、公式ドキュメント、実行結果を確認する。
Memory だけを根拠に昇格しない。

既存の authored skill も調べる。
同じ目的のskillがあれば新設せず、そのskillへの小さな更新として評価する。

## 昇格基準

次のいずれかを満たす候補だけを昇格対象にする。

- 独立した複数セッションで同じ手順や失敗が現れた。
- ユーザーが再利用する規則または手順として明示した。
- 再現可能で、再発時の損失が大きい失敗と修正である。

さらに、次をすべて満たす必要がある。

- 現在のリポジトリまたは実動確認で内容を裏付けられる。
- 特定セッションの途中状態ではなく、6か月後にも使える。
- 既存の規範やskillと矛盾せず、重複もしない。
- 秘密、セッションID、費用、個別プロジェクト名、不要な絶対パスを含まない。
- OMPで実在するtool名、内部URL、承認手順へ直されている。

一度だけ成功したコマンド、一般化できない回避策、推測、古いリポジトリ状態は昇格しない。

## 着地先

候補の内容に合わせて着地先を選ぶ。

| 内容 | 着地先 |
|---|---|
| 複数リポジトリで再利用する手順 | `~/dotfiles/agents/skills/<name>/SKILL.md` |
| プロジェクト固有の手順 | そのリポジトリで既に使われているskillディレクトリ |
| エージェントの常時規範 | 該当するinstructionsファイル |
| 機械的に保証すべき挙動 | コード、設定、hook、テスト |
| 再発したbugの機械検査pattern | そのrepoの`.semgrep.yaml`。repoを問わず誤検知がほぼ出ない場合のみ`~/dotfiles/semgrep/default.yaml` |
| 単なる過去事実 | memoryに残し、skillへ昇格しない |

プロジェクトにskillの既存規約がなければ、新しい配置規約を無断で作らずmanaged skillのまま保留する。
コードで保証できる内容を、手順文だけで代替しない。

## 提案と承認

変更前に候補を次の表で提示する。

| 候補 | 根拠 | 判定 | 着地先 | 変更 |
|---|---|---|---|---|
| 名前 | 現在の証拠 | 昇格、統合、保留、却下 | パス | 差分の要点 |

昇格または既存ファイルの変更は、候補ごとにユーザー承認を取る。
承認前に authored skill、instructions、コード、設定を変更しない。
managed skillの削除も承認対象に含める。

候補がなければ、確認した三系統と「昇格対象なし」を報告して終了する。

## 昇格

承認された候補だけを適用する。

- 既存skillに同じ責務があれば、重複部分を作らず既存skillへ統合する。
- 新しいskillのfrontmatterには、具体的な発火条件を `description` に書く。
- セッションの時系列や作業ログを転記せず、再利用する判断条件と手順だけを残す。
- Claude Code、Codexなど別基盤のtool名が混ざっていればOMPの語彙へ変換する。
- グローバルskillを新設した場合は `~/dotfiles/scripts/link` で共有skillのsymlinkを作る。
- 昇格済みmanaged skillは、authored側の実動確認後にだけ削除する。
- `learned.md` とlocal memory生成物は履歴・再統合の入力なので、昇格を理由に削除しない。

commitとpushは、ユーザーが依頼した場合だけ行う。

## 実動確認

変更した表面に対応する最小の確認を行う。

- skill：frontmatter、参照パス、tool名を確認し、新しいOMPセッションで発火条件に一致することを確認する。
- 設定：新しいOMPプロセスが有効値を読み込むことを確認する。
- scriptまたはhook：実際の入口を起動し、対象経路を一度通す。
- コード：変更した契約を再現する実行または既存テストを使う。

新しいOMPセッションでなければ確認できない変更は、その場で確認済みと扱わず、再起動後に必要な操作を明記する。

最後に、昇格、統合、保留、却下と、各確認結果を簡潔に報告する。
