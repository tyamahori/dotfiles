# grill-me

設計判断を依存順に問い直し、実装後の手戻りにつながる暗黙の前提を実装前に解消する。
通常の入口は `task-briefing` のままとし、本スキルは合意済みの枠組みを詳しく検討する任意の後段として使う。

## task-briefing との境界

入力は、合意済みのタスクブリーフィング、具体的な計画、または検討対象が明確な設計判断とする。
課題、検証可能なゴール、Why、成果物の形が未確定なら、先に `task-briefing` を使う。
すでに確定している項目は聞き直さない。

`task-briefing` は着手可能な枠組みを作る。
`grill-me` は、その枠組みの中にある意思決定と依存関係を検討する。
通常の曖昧な依頼を理由に、本スキルを自動で開始してはならない。

## 事実を先に調べる

コード、設定、履歴、issue、PR、実行結果から分かる事実は、質問する前に自分で確認する。
複数の調査が独立していれば subagent へ並列に渡してよい。
調査中の事実に依存する質問だけを保留し、ほかの判断は先に進める。

ユーザーに聞くのは、価値判断、優先順位、許容するトレードオフなど、本人が決める必要のある事項だけとする。
情報不足と意思決定を混同しない。

## 設計ツリーを作る

検討対象を設計ツリーとして管理する。
ノードは意思決定、辺は「この判断が決まらないと次を決められない」という依存関係を表す。
前提が解決済みで、今回答えられる未決定ノードの集合を frontier と呼ぶ。

設計ツリーは内部の作業状態であり、ユーザーが求めない限り毎回全文を表示しない。
回答を受けるたびにツリーを更新する。
回答が上流の前提を変えた場合は、影響する下流ノードを未決定へ戻す。

## frontier 単位で質問する

一度に一問ずつではなく、互いに依存しない frontier の質問を一ラウンドに2〜4問まとめる。
一つの回答に依存する質問を同じラウンドへ入れてはならない。
frontier が一問だけの場合や、回答によって後続が大きく変わる場合は一問でよい。

各質問には次を含める。

1. 決める事項
2. この判断が成果物やリスクをどう変えるか
3. 2〜5個の実質的に異なる選択肢
4. 推奨回答
5. 推奨理由と主要なトレードオフ

構造化された質問ツールが使える環境では、そのツールで一ラウンドをまとめて聞く。
使えない環境では `Q1`、`Q2` のように番号を付けて平文で聞く。
選択肢で表せない判断を、無理に二択へ落とさない。

## 検討する枝を限定する

次のいずれかを変えうる判断だけを掘る。

- ゴールと観測可能な成功条件
- スコープと非スコープ
- ユーザー向け挙動、外部 API、共有 interface
- データ状態、移行、互換性、切り戻し
- 権限、認証、機密情報、システム境界
- 失敗時の挙動と運用上の復旧方法
- 成果物の形と耐久性

既存規約やリポジトリから一意に決まる実装詳細はエージェントが選ぶ。
将来ありうる要求を想像して枝を増やさない。
「徹底的に」は、結果やリスクを変えない仮定まで列挙することを意味しない。

## 終了条件

成果物またはリスクを変えうる未決定ノードがなくなったら、`task-briefing` の `references/checklist.md` を読み、同じテンプレートでブリーフィングを更新する。
別形式の詳細設計書は作らない。
主要な意思決定、棄却した案、残存リスクは、後の実装判断に必要なものだけブリーフィングへ添える。
ファイルへの保存や ADR の作成は、ユーザーの依頼またはリポジトリの既存 workflow が求める場合に限る。

更新したブリーフィングを提示し、共通理解に達したか確認する。
ユーザーが確認するまで、実装、ファイル編集、issue 作成、PR 作成へ進まない。
確認後に実装を求められたら、更新済みブリーフィングを coordinator と worker の共有契約として使う。
